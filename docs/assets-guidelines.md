# Правила роботи з графічними ресурсами

## Розташування

- Корпоративні ресурси, спільні для кількох продуктів, зберігаються у `shared/assets/`.
- Корпоративні логотипи зберігаються у `shared/assets/logos/`, а отримані оригінали — у `shared/assets/logos/originals/`.
- Ресурси конкретного продукту зберігаються лише у `brands/<product>/assets/`: логотипи — у `logos/`, паковання — у `packaging/`, інші продуктові зображення — у `images/`.
- Згенеровані картки, презентації та інші результати належать до `exports/` і не змішуються з вихідними матеріалами.

## Найменування файлів

- Використовувати латиницю, нижній регістр і kebab-case.
- Назва має коротко описувати вміст і, за потреби, ракурс, мову або версію: `package-front-uk-v1.png`.
- Не використовувати пробіли, службові назви на кшталт `final-final` або непояснені числові суфікси.
- Не перейменовувати отриманий оригінал без погодження. Нормалізовану копію слід створювати як окремий файл із простежуваним походженням.

## Підтримувані формати

- `SVG` — пріоритетний формат для логотипів, піктограм та іншої векторної графіки.
- `PNG` — растрові зображення з прозорістю або без втрат.
- `JPG` / `JPEG` — фотографії без потреби у прозорості.
- `WebP` — оптимізовані растрові ресурси для цифрового використання.
- `PDF` — вихідні векторні макети або затверджені документи; не використовувати як заміну каталогу зображень.

Формат файлу має відповідати його фактичному вмісту, а не лише розширенню.

## Логотипи та прозорість

- Не деформувати, не розтягувати, не стискати й не обрізати логотип.
- Зберігати оригінальні пропорції, охоронне поле та затверджені кольори.
- Для накладання на змінний фон використовувати SVG або PNG/WebP із прозорим фоном.
- Не видаляти фон з оригіналу автоматично. Версію з прозорістю створювати окремо й документувати її походження.
- Не додавати тіні, контури, градієнти чи інші ефекти без затверджених бренд-правил.

## Зображення паковання

- Зберігати оригінальні пропорції упаковки.
- Не виправляти перспективу, кольори, написи або геометрію в оригінальному файлі.
- Оброблені версії зберігати окремо від оригіналу та позначати в маніфесті.
- Не використовувати зображення паковання для іншого продукту без окремої перевірки.

## Оригінали та похідні файли

- Оригінальні файли є незмінними джерелами.
- Похідні ресурси повинні мати окреме ім'я, призначення та запис у продуктовому маніфесті.
- Експортовані матеріали не повертаються до каталогів оригінальних ресурсів.
- Перед додаванням бінарного файлу до Git перевіряти розмір. Файли понад 50 MB потребують окремого рішення щодо Git LFS; Git LFS не встановлюється автоматично.

### Ресурси з непідтвердженими правами

- Оригінали з непідтвердженими правами використання зберігаються локально й не додаються до Git.
- Manifest позначає такий набір через `distribution.status: local-only-unconfirmed-rights` і `trackedInGit: false`.
- `npm run validate:assets` допускає відсутність лише явно позначених локальних оригіналів, щоб репозиторій залишався перевірюваним після клонування.
- `npm run validate:assets:strict` вимагає наявності всіх оригіналів і запускається перед локальною роботою з графікою.
- Після підтвердження прав статус distribution і правила `.gitignore` змінюються окремим погодженим завданням.

## Маніфест продукту

Кожен `brands/<product>/assets/asset-manifest.json` містить ідентифікатор продукту та масив `assets`. Для майбутнього запису ресурсу передбачені поля:

- `id`;
- `path` — шлях відносно директорії продукту, наприклад `assets/packaging/package-front.png`;
- `type`;
- `format`;
- `description`;
- `usage`;
- `status`.

До маніфесту додаються лише достовірні метадані. Невідомі значення залишаються `null`; відсутні ресурси не описуються вигаданими записами.

Спільні ресурси реєструються в `shared/assets/asset-manifest.json` шляхами від кореня проєкту. Продуктні шляхи залишаються відносними до відповідної директорії `brands/<product>/`.

Технічна придатність, візуальна якість і approval status фіксуються окремо. Успішне декодування або достатня роздільна здатність не означають, що ресурс затверджено для публікації. До явного погодження використовується статус `needs-review` і approval status `unconfirmed`.

Після додавання або зміни ресурсу потрібно оновити checksum та metadata в manifest і запустити `npm run validate:assets`.

## Повторне використання

Спочатку перевіряти `shared/assets/` і наявні продуктові маніфести. Спільний ресурс зберігається в одному канонічному місці та повторно використовується за посиланням; дублікати в продуктових каталогах не створюються без технічної необхідності.
