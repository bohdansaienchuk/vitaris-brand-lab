# Архітектура Vitaris Brand Lab

## Призначення

Vitaris Brand Lab розділяє перевірені продуктові дані, навчальний контент, брендове оформлення та майбутню логіку генерації. Такий поділ дає змогу повторно використовувати шаблони й компоненти без змішування фактів із візуальним представленням.

## Рівні системи

### `brands/`

Кожен продукт має однакову структуру:

- `product-data.json` — машинозчитувані перевірені дані;
- `product.md` — розширений опис продукту для редакторської роботи;
- `brand.md` — позиціонування, аудиторії та комунікаційні рамки;
- `content/` — навчальний контент за тематичними секціями;
- `assets/` — логотипи, зображення паковання та інші вихідні зображення;
- `design/brand-tokens.json` — лише індивідуальні параметри бренду.

Фактичні дані не повинні зберігатися лише у візуальних шаблонах. Джерело кожного медичного або продуктного твердження має бути простежуваним.

### `shared/`

- `assets/` містить спільні корпоративні логотипи, іконки, ілюстрації та фонові зображення. Оригінали корпоративних логотипів зберігаються окремо в `assets/logos/originals/`.
- `design-system/` містить спільні кольори, типографіку, відступи й токени. Базові орієнтири: 1080 × 1920 px, 9:16, Oswald Bold для заголовків та Inter для основного тексту.
- `components/` призначено для повторно використовуваних блоків майбутнього рендерингу.
- `templates/cards/` міститиме шаблони семи типів матеріалів: огляд продукту, інгредієнти й механізми, ключові переваги, медичні спеціальності, наукові дані, навчання продажів і порівняння продуктів.
- `templates/presentations/` міститиме спільні шаблони презентацій.

Бренди посилаються на спільні правила й перевизначають лише дозволені бренд-токени. Копіювати спільні компоненти або шаблони в кожну продуктну директорію не слід.

Продуктні графічні ресурси зберігаються в `brands/<product>/assets/` і реєструються в `asset-manifest.json` шляхами відносно директорії продукту. Оригінальні ресурси не змішуються зі згенерованими файлами в `exports/`.

### `scripts/`, `tests/` та `exports/`

- `scripts/` у майбутньому міститиме TypeScript-сценарії валідації, генерації та керування Playwright.
- `tests/` міститиме структурні, контентні та візуальні перевірки.
- `exports/png/` і `exports/pdf/` є локальними каталогами результатів та ігноруються Git.

## Потік даних

Перевірені джерела → структуровані дані продукту → редакційний контент → спільний шаблон + бренд-токени → перевірка для смартфона → PNG/PDF.

## Принципи розширення

1. Новий продукт отримує ту саму структуру, що й наявні п'ять продуктів.
2. Повторюваний візуальний патерн спочатку додається до `shared/`.
3. Особливості бренду описуються даними, а не копіями компонентів.
4. Контент залишається незалежним від конкретного способу рендерингу.
5. Генератор повинен відхиляти невалідні дані, а не заповнювати прогалини припущеннями.
